# Защита snapshot, используемого восстановлением

Статус: отложенный проект, реализация отсутствует. Этот PR сохраняет протокол для будущей работы; текущую очистку он не меняет.

## Проблема

Потребитель может восстанавливать том из snapshot, когда retention удаляет исходный VolumeSnapshot. Импорт того же snapshotHandle через другой VolumeSnapshotContent с Retain не защищает облачный snapshot от удаления через исходный объект с Delete.

Разнесение расписаний уменьшает вероятность пересечения, но не закрывает восстановление дольше суток, ручные запуски и повторные попытки.

## Предлагаемый протокол

Для каждого исходного VolumeSnapshot UID существует одна запись координации в выделенном инфраструктурном namespace. Первая версия может использовать ConfigMap; имя детерминировано UID. В записи хранятся namespace/name/UID источника, UID VolumeSnapshotContent, идентификатор backend snapshot, состояние удаления и набор потребителей с идентификаторами операций.

Закрепление потребителем и разрешение удаления меняют одну запись через compare-and-swap по resourceVersion:

- Потребитель добавляет свою операцию только если удаление ещё не разрешено.
- Очистка переводит запись в Deleting только при отсутствии потребителей.
- Конфликт требует нового чтения и повторной проверки. Нельзя принимать решение по кешу.
- Если записи нет, обе стороны создают одно и то же имя; AlreadyExists требует перечитать запись.
- Deleting запрещает новые закрепления. Состояние сохраняется после рестарта очистки до подтверждённого завершения удаления; неопределённый результат DELETE не возвращает snapshot в доступное состояние.
- После закрепления потребитель повторно проверяет исходный UID, readyToUse, связанный content/handle и отсутствие deletionTimestamp.
- DELETE исходного объекта использует UID precondition.

Закрепления не снимаются по TTL или исчезновению Job. Deadline вызывает уведомление. Явная отмена сначала останавливает владельца операции и незавершённое provisioning, затем снимает закрепление. Удаление записей координации и повторное использование имён не должны открывать гонку со старым процессом.

Ошибка чтения или обновления реестра означает пропуск удаления. Потребитель при ошибке закрепления не начинает разрушительную часть восстановления.

Это защита от участвующей в протоколе очистки. Внешнее удаление через облачный API и ручное удаление администратором требуют отдельной политики доступа.

## Изменения retention

- Для настроенных источников сохранять заданное число последних готовых snapshots и дополнительно все закреплённые.
- Незавершённый или ошибочный новый snapshot не вытесняет последний готовый.
- Импортированные snapshots с spec.source.volumeSnapshotContentName пропускать: текущий прямой доступ к persistentVolumeClaimName несовместим с ними.
- Подтвердить критерии владения snapshot перед очисткой.
- Добавить метрики пропущенных удалений, возраста закреплений и ошибок координации.

## Ввод в работу

Сначала развернуть реестр/RBAC и новую очистку, затем дождаться завершения всех старых Jobs. Только после этого включать потребителей. Старый процесс удаления не соблюдает закрепления.

## Критерии проверки

- Одновременные закрепление и удаление: только одно действие разрешается.
- Несколько потребителей; снятие одного закрепления не разрешает удаление.
- Рестарт обеих сторон, неопределённый результат API, конфликт resourceVersion.
- Просроченное закрепление и отсутствующий Job сохраняют snapshot.
- Snapshot уже удаляется, имеет другой UID, не готов или содержит ошибку.
- Повторный запуск очистки после Deleting.
- Импортированный snapshot не вызывает исключение и не удаляется.
- Новая неготовая копия не вытесняет последнюю готовую.
- Восстановление пересекает следующую суточную ротацию.
